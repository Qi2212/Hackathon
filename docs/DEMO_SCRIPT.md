## 二、完整主线：8–10 分钟

### 0:00–0:45｜开场：我们解决什么问题

**操作：**展示账号选择页，暂不进入细节。

**讲稿：**

大家好，我们的项目叫 CampusGrove，是一个面向校园的 GPU 算力互助平台。

我们关注一个很常见的矛盾：有些同学做实验时一直在等卡，但另一些实验室工作站和个人 GPU，在某些时间段其实是闲置的。资源存在，却很难知道谁能借、什么时候能借，以及借用后怎样保障卡主的权益。

我们的目标，是把这些分散的空闲时段连接起来，让借用者能看懂资源、比较方案并发起申请，也让贡献者保留对个人 GPU 的授权权利。

接下来我会用一名学生的身份，完整演示一次从发现资源到申请、运行和释放的流程。当前使用合成数据展示系统行为，不会在真实 GPU 上训练模型。

### 0:45–1:20｜选择身份：同一个人可以借卡，也可以贡献

**操作：**选择林同学，进入工作空间。指一下左下角当前账号和首页指标。

**讲稿：**

这里提供了几个测试账号。我先选择林同学，他既可以申请别人的算力，也拥有自己的 GPU。

进入后，可以看到当前可用资源、自己的运行任务、等待任务和历史贡献收益。这些信息都围绕当前个人展开；切换身份后，个人画像、任务和审批内容也会切换。

测试账号不需要密码，是为了便于展示多角色流程。正式产品还需要接入学校或组织的身份认证。

**停顿提示：**首页加载完成后再继续，不要逐个念所有数字。

### 1:20–2:25｜算力大厅：看得见卡，也看得懂归属与计划

**操作：**向下滚动到资源卡区域。先指公共资源，再点击一张个人 GPU，例如林同学的 `vision-ws-01`。展示“计划与可用性”，再切换“规格与收益”，最后关闭详情。

**讲稿：**

算力大厅里，每个 3D 小电脑代表一张 GPU。我们把同一工作站的 GPU 按每排四张排列，能直接区分空闲、任务占用、卡主自用和离线状态。

资源还区分不同的使用范围：大厅公共卡面向全校，实验室公共卡面向本实验室，协作组公共卡面向组内成员。个人私有卡可以被发现，但借用仍然需要卡主同意。

点开这张个人卡，不只是查看型号和显存，还可以查看卡主项目的计划进度，以及未来的条件共享时段。这能帮助借用者判断，自己的实验是否适合安排在这个窗口。

这里的曲线来自预制项目计划，是演示数据；它表达的是计划和共享意愿，并不代表真实 GPU 监控，也不保证这个时段一定能拿到资源。

**重点：**强调“资源规格 + 归属 + 共享计划”，不要逐一讲解全部图表。

### 2:25–3:40｜提交实验：一份需求，得到可解释的分析

**操作：**点击“新建实验”或“提交实验”，按主流程填写卡填写。点击“分析当前实验”，滚动到深色结论卡片。

**讲稿：**

现在我准备做一次多模态检索实验。这里使用一张统一表单，研究目标、资源约束、预算和后续申请共用同一份输入，不需要重复填写。

我选择一张 H100、约 20 GB 的最低显存、30 分钟和 20 积分预算，范围限定为公共大厅。

点击分析后，系统会结合当前演示资源，给出任务拆解、候选节点、预计费用、条件开始和结束时间，以及需要注意的风险。

例如，训练任务会拆成数据准备、训练验证、保存检查点和生成报告。费用按照卡数、时长和节点单价计算。这组 H100 参数的使用估价约为 2.4 积分。

当前分析使用本地模拟 API，目的是展示接口交互和可解释的分析流程，无需真实 API key。它不会声称已经测量过真实训练吞吐，也不会凭空保证多卡一定能加速。

**停顿提示：**用鼠标指结论、费用、候选节点和风险原因，每项只讲一句。

### 3:40–4:35｜改变输入：证明分析会随需求变化

**操作 A：**预算改为 0，重新点击分析，指“预算不足”。

**讲稿：**

我先把预算改为零。系统会明确指出预估费用超过预算，提醒我调整预算、规格或时长。

**操作 B：**预算恢复 20，型号改为 RTX 4090，最低显存改为约 80 GB，重新分析。

**讲稿：**

再把需求改成 RTX 4090，但要求约 80 GB 显存。这个组合超过了当前这类卡的规格，系统会返回没有兼容资源窗口，而不是给出一个看似合理、实际无法执行的推荐。

如果改成推理任务，执行步骤会变为分批推理和结果汇总；如果不接受中断，分析会建议稳定优先。输入变化后，需要重新分析和生成方案，旧方案不会被直接用于新的需求。

**操作 C：**恢复主流程填写卡中的 H100、约 20 GB、20 积分等参数，重新分析。

**不要这样讲：**“AI 已经知道实验实际要跑多久。”当前时长沿用用户填写值，没有真实训练测量。

### 4:35–5:45｜比较方案：从建议进入可确认的申请

**操作：**点击“生成方案与预估”，展示经济、算力、稳定、均衡四种方案。确认“你更在意什么”为综合均衡，指右侧队列预测和下方最终摘要。

**讲稿：**

分析帮助我们理解需求，下一步是把需求变成可以核对的资源方案。

这里提供经济、算力、稳定和综合均衡四种策略。同一组需求下，它们可能选择同一个节点；资源条件不同时，成本、性能和回收风险的权衡才会体现出差异。我们不会为了演示差异，强行生成四个不同结果。

右侧显示对应方案的队列、条件顺位、等待原因，以及预计开始和结束时间。下方则给出最终确认摘要，包括目标节点和预计费用。

这一步还没有占用 GPU。预测假设现有租约按时结束，不包含所有未来竞争和续租，因此它不是预约承诺。正式提交会复用这份已核对的方案，再执行实际资源校验。

**停顿提示：**若预测显示需要等待，直接解释其前提；不要承诺等到预测时间系统就会自动启动。

### 5:45–6:40｜申请与任务状态：看到一次接口驱动的变化

**操作：**核对摘要，点击“确认摘要并申请”。进入“我的任务”，找到“校园多模态检索演示”。确认状态后主动释放这条新任务，再返回大厅查看空闲资源变化。不要释放预置任务。

**讲稿：**

确认后，系统会通过后端申请资源，并在模拟环境中建立任务。这里可以看到刚刚提交的实验，以及分配、运行和租约信息。

页面展示的不是一张固定原型图，申请会改变本地资源账本和任务状态。实验结束后，我们主动释放资源，让这张卡重新变成可用资源。

需要区分的是：这里演示的是系统状态流转，没有真正执行模型训练；租约到期时间也不等于训练一定完成。当前还没有完整的等待任务自动派发和租约自动释放，所以现场使用可直接申请的公共资源，并手动释放。

**若未进入运行：**先看页面提示。若容量已变化，返回大厅确认空闲状态，重新生成方案；不要反复点提交。

### 6:40–7:25｜队列与画像：让等待有解释，让用户有自己的视角

**操作：**打开“队列与预测”，展示林同学已有的等待任务摘要；然后打开“个人画像”。

**讲稿：**

对于需要等待的任务，我们不希望只显示一个“排队中”。这里可以看到自己的顺位、前序任务数量、兼容容量、阻塞原因和条件预测依据。

现在看到的等待任务包含内置演示样本，不是刚刚那个已经释放的实验。当前 Pending 还不会完整自动派发，页面主要展示如何解释等待。

个人画像则从当前用户的实验和交互样本出发，展示研究习惯、资源共享和协作特征。它描述的是一个人，不是把实验室信息当作个人画像；目前属于可解释的演示统计基线。

### 7:25–8:35｜贡献与协作：为什么有人愿意把卡放进来

**操作：**打开“贡献资源”，展示登记表和“登记为草稿”按钮；若时间足够，登记一台名为“路演工作站”的模拟 GPU，核对后发布，最后在没有活动租约时撤回。再简要打开“收支与收益”和“资源小组”。

**讲稿：**

除了借卡，用户也可以登记自己的闲置工作站。登记先生成草稿，核对并明确发布后，才会进入演示资源池。发布的个人卡仍然保留审批权；没有活动租约时可以撤回。

这里登记的是用户声明的模拟资源，还没有进行真实硬件探测和节点 Agent 接入。

在收益页面，可以看到资源来源、贡献者所得和平台分配，解释“为什么愿意贡献”。当前近 30 日收支是合成历史样本，不会因为刚才的新任务立刻增加一笔历史收入。

实验室也可以通过协作组共享公共卡，同时保留成员个人卡的私有属性。目前已经展示预制小组和资源可见规则，自助创建、邀请和成员管理是下一步的工作。

**时间控制：**剩余时间不足时，只展示登记与发布入口，不进行实际登记；主线仍然完整。

### 8:35–9:10｜收尾：用一句话说明价值

**操作：**回到算力大厅，或打开使用指南的项目介绍。

**讲稿：**

CampusGrove 希望让校园里分散的 GPU 从“需要到处问谁有空卡”，变成一个可以看见资源、理解计划、比较方案、确认授权并追踪结果的互助流程。

这次 Demo 已经把资源发现、输入分析、方案比较、申请、任务状态和共享协作串在一起。接下来我们会重点完善真实节点接入、自动调度和完整的资源生命周期，让这个流程逐步走向实际使用。谢谢大家。

## 三、加演：私有卡审批，约 2–3 分钟

适合评委问“个人卡凭什么愿意共享、怎么控制授权”时展示。建议主流程完成后再加演。

### 1. 林同学发起申请

**操作：**回到提交实验，实验名设为“跨实验室私有卡借用演示”；选择 RTX 3090、1 张、约 20 GB、30 分钟、预算 20，分析范围恢复“实验室优先，兼顾大厅”。分析并生成方案后，先核对目标是否为周同学的 `bio-ws-01`。

**讲稿：**

个人 GPU 的可发现性，不等于任何人都能直接使用。现在我申请周同学的一张 RTX 3090。提交后，申请会进入卡主的现场审批，而不是直接替他占用 GPU。

**注意：**若目标不是 `bio-ws-01` 或资源不再可行，以界面实际结果为准；不要把另一个人的 GPU 说成周同学的。可以只展示归属与审批要求。

### 2. 切换周同学审批

**操作：**发出审批后点击左下角切换账号，选择周同学；在“共享审批”的“现场申请”区域找到刚才的实验，点击“同意共享”。

**讲稿：**

切换成卡主后，他可以看到申请方和申请内容，并决定是否共享。个人卡的所有权和授权边界仍然属于贡献者。

不要把旁边的预制审核案例当作这次申请。预制案例用于展示批准、拒绝和协商的状态；现场申请才关联这次实际创建的决策。

### 3. 切回林同学完成提交

**操作：**切回林同学，在“共享审批”的现场申请区域找到已批准记录，点击“确认条件并提交”；进入任务页检查状态，结束后主动释放。

**讲稿：**

卡主同意后，再由申请人确认条件并提交。这样既能让闲置资源流动，也保留了贡献者对个人 GPU 的控制权。当前预测时间不包含审批等待，因此实际开始时间还取决于双方确认和提交时的容量校验。

### 可直接朗读的短稿

大家好，我们的项目是 CampusGrove，一个校园 GPU 算力互助平台。我们希望解决“有人做实验排不到卡，但另外一些工作站又在闲置”的问题。

我先用林同学登录。大厅里的每个 3D 小电脑代表一张 GPU，能看到它的状态和来源。点开个人卡，还可以看到卡主计划和条件共享窗口，帮助判断什么时候适合借用。个人卡始终保留卡主授权。

接下来提交实验。我们只填一份需求，系统就能分析任务步骤、候选资源、费用和风险。比如这一张 H100 运行半小时，使用估价约 2.4 积分。如果把预算改成零，系统会明确指出预算不足；如果要求的显存超过卡的规格，也会提示没有兼容资源。

恢复可行参数后，我们生成资源方案，核对成本和条件时间，再确认申请。任务页会显示刚创建的任务，释放后资源重新可用。这些变化由后端接口驱动，当前使用合成数据和模拟任务，没有真实执行 GPU 训练。

CampusGrove 的价值，是把“到处找人问有没有卡”，变成可发现、可解释、有授权、有记录的校园算力互助流程。接下来我们会完善真实节点接入和自动调度。谢谢大家。

## 五、常见提问与回答

### 这是写死的原型页面吗？

不是。资源展示、分析、方案、申请、任务、审批和资源发布都连接了本地后端接口，操作会改变模拟状态。但资源和历史数据是合成样本，任务不会真的训练模型。

### 你们真的接了大模型吗？

这次提交页演示使用本地模拟 API，重点验证输入到分析、再到方案确认的产品流程。项目另有可选模型适配，但不能把本次模拟结果说成真实模型调用。资源硬约束和权限也不应由模型自由决定。

### 预测开始和结束时间是怎么来的？

分析会参考可见节点、规格和现有租约释放时间，结束时间再结合用户填写的时长推算；队列页还展示前序与阻塞依据。未完全覆盖续租、新竞争和审批耗时，所以是条件估计，不是保证。

### 为什么我多填几张卡，没有说一定更快？

多卡的实际加速取决于模型、并行方式、数据和通信。当前没有真实性能测量，时长以用户输入为准；系统主要检查同节点卡数约束，并计算相应资源成本。

### 卡主临时要用怎么办？

设计上通过共享窗口、通知期和检查点降低冲突。当前可展示相关状态与手动操作，但还没有完整的自动回收、迁移和恢复闭环，不能承诺无损恢复。

### 实验室的卡和个人卡会混在一起吗？

归属分别记录。实验室 / 协作组公共卡按成员范围开放；成员的个人卡继续保留个人审批。当前小组为预制场景，尚未实现自助创建和邀请。

### 收益能直接结算成钱吗？

当前界面用积分和合成历史展示贡献激励与平台分配，不代表真实支付、提现或商业结算；现场新任务也不会直接进入近 30 日历史汇总。

### 不接真实 GPU，这次验证了什么？

验证了产品流程、资源与身份边界、输入约束分析、多策略比较、申请审批、状态变化和解释性展示。真实硬件接入、调度可靠性和性能收益，还需要下一阶段实际环境验证。

## 六、现场卡住时的接话与处理

| 情况 | 先做什么 | 可以这样说 |
| --- | --- | --- |
| 分析提示不兼容 | 核对型号、显存、卡数；恢复主流程参数 | “系统识别出这组约束无法满足，我调整到可行配置继续。” |
| 方案暂不可行 | 看空闲容量与范围，释放自己的排练任务，再重新生成 | “资源状态会变化，提交前需要按当前容量重新校验。” |
| 任务服务未连接 | 检查两个健康接口；先展示大厅与详情，暂停提交 | “资源展示和任务服务分别运行，我先展示资源发现和计划部分。” |
| Pending 没自动运行 | 展示队列原因，回到可用公共资源主流程 | “这一版还没有完整自动派发，这里展示的是有依据的等待预测。” |
| 审批后任务没启动 | 回申请人账号，在现场申请里确认提交 | “审批和提交分为两步，授权后仍由申请人确认条件。” |
| 页面还是旧版本 | Ctrl + F5；必要时重启后端 | “我刷新一下当前演示版本。” |

不要用“真实训练正在跑”“等到这个时间一定拿到卡”“所有功能都已完成”等说法掩盖现场状态。准确说明当前完成的流程和边界，更方便展示项目的实际价值。
